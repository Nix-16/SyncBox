## 1. 产品定位

SyncBox 是一个 **C++17 编写的跨平台双向文件同步工具**，采用**中心服务器 + 多客户端**架构，支持 Windows、Linux、macOS。

核心价值主张：

1. **不丢数据**：任何无法安全合并的修改都保留冲突副本，绝不静默覆盖用户文件。
2. **离线可用**：断网期间本地修改完整保留，恢复连接后自动补齐。
3. **状态可恢复**：进程崩溃、断电、重复请求、事件丢失都不会导致索引与磁盘不一致。
4. **跨平台一致**：三个平台共享同一套协议、版本模型、冲突策略与核心同步逻辑。

## 2. 产品目标（可度量）

| 编号 | 目标 | 度量方式 |
|---|---|---|
| G-1 | 多设备目录内容最终一致 | 所有设备空闲后，抽查文件 SHA-256 与服务端一致率 100% |
| G-2 | 不丢失用户数据 | 冲突场景测试中，任意一方修改内容在本地磁盘或冲突副本中可找回，丢失率 0 |
| G-3 | 离线期间修改不丢 | 断网 30 分钟后恢复，所有离线修改在 5 分钟内同步完成 |
| G-4 | 崩溃可恢复 | 在任意阶段 `SIGKILL` 客户端，重启后 60 秒内自愈且不产生重复版本 |
| G-5 | 幂等 | 同一 `op_id` 重放任意次数，服务端版本数不增加 |
| G-6 | 三平台行为一致 | 同一组集成测试在 Linux/Windows/macOS 全绿 |

## 3. 目标用户与使用场景

### 3.1 用户角色

| 角色 | 描述 | 关注点 |
|---|---|---|
| 个人用户 | 2–5 台自有设备（台式机 + 笔记本 + Mac） | 无感同步、冲突可理解 |
| 小团队 | 3–20 台设备共享一个同步空间 | 权限、设备撤销、服务端可运维 |
| 开发者（项目作者） | 求职作品集的评审者 | 架构清晰、测试真实、文档与代码一致 |

### 3.2 典型场景

- **S1 单文件修改传播**：设备 A 修改 `docs/spec.md`，设备 B、C 在 2 秒内收到更新。
- **S2 离线编辑**：设备 B 断网，修改 3 个文件、删除 1 个、新建 2 个；恢复网络后全部同步，且不覆盖设备 A 在同期做的修改。
- **S3 并发修改同一文件**：A、B 同时基于 revision 7 修改 `notes.txt`；先提交者胜出，后提交者的内容写入冲突副本 `notes (conflict <device> <time>).txt`，两份都在。
- **S4 删除 vs 修改**：A 删除 `old.txt`，B 同期修改它。修改胜出，文件恢复并产生冲突记录。
- **S5 重命名与移动**：A 把 `a/b.txt` 移到 `c/b.txt`，B 同时修改其内容；重命名与内容修改都被保留（若基于同一 revision 冲突则按冲突策略处理）。
- **S6 旧设备复活已删除文件**：设备 C 离线 3 个月后上线，其中仍有已删除文件；不得把它重新上传为有效文件。
- **S7 进程崩溃**：客户端在“已下载但未替换”阶段被 kill -9；重启后临时文件被清理，目标文件不出现半截内容。
- **S8 重复请求**：客户端提交后网络超时但服务端已成功，客户端重试；服务端返回同一结果，不产生 revision 8 和 9。
- **S9 文件监控事件丢失**：inotify 队列溢出；周期性全量核对发现差异并补齐。
- **S10 跨平台命名**：Linux 设备创建 `Report.TXT` 与 `report.txt`；Windows 设备无法共存，系统必须检测并给出确定性处理（见 [CONFLICTS.md](CONFLICTS.md) §7）。

## 4. 术语表

| 术语 | 定义 |
|---|---|
| Space（同步空间） | 服务端的一个逻辑共享目录，多设备加入同一 space 即互为同步方 |
| `space_id` | 空间 UUIDv7 |
| `device_id` | 设备 UUIDv7，注册时由服务端分配 |
| `file_id` | 文件稳定标识，服务端在 create 时分配，重命名/移动后不变 |
| `revision` | 单个文件在服务端单调递增的版本号，从 1 开始 |
| `parent_revision` | 本次提交所基于的父版本号，用于乐观并发控制（CAS） |
| `op_id` | 客户端生成的一次逻辑操作 UUIDv7，用于幂等 |
| `seq` | 服务端**全局**单调递增变更序号，作为同步游标 |
| `content_hash` | 文件内容的 SHA-256（64 位小写十六进制） |
| `blob` | 按 `content_hash` 去重存储的文件内容单元 |
| Tombstone | 删除标记记录（`deleted=1`），保留以阻止旧设备复活文件 |
| 冲突副本 | 无法合并时新建的文件，命名见 [CONFLICTS.md](CONFLICTS.md) §5 |
| 全量核对 | 将本地索引/磁盘与服务端快照逐项比对的修复流程 |

## 5. 功能需求

每条需求均给出**验收条件**。里程碑归属见 [ROADMAP.md](ROADMAP.md)。

### FR-01 设备注册与配置

- 用户通过一次性 **enrollment token** 注册设备，获得 `device_id` 与长期 `device_token`。
- 配置项包括：服务器地址、同步目录、忽略规则、并发数、日志级别。
- 支持设备撤销；撤销后该设备的所有请求返回 `403 DEVICE_REVOKED`。

**验收**：有效 token 注册成功并落库；过期/已用 token 返回 `401`；撤销后旧 token 立即失效。

### FR-02 中心服务器通信

- HTTP/1.1 + JSON over TLS（Boost.Beast）。
- WebSocket 用于在线变更通知（仅提示，不作为数据通道）。
- 所有请求携带协议版本，服务端拒绝不兼容版本。

**验收**：[PROTOCOL.md](PROTOCOL.md) 列出的每个端点有对应集成测试。

### FR-03 文件监控、增量索引与周期核对

- Linux: inotify；Windows: ReadDirectoryChangesW；macOS: FSEvents。
- 事件去抖（默认 300 ms），批量提交。
- 每 60 秒（可配置）做一次轻量核对；每 24 小时（可配置）做一次全量核对。

**验收**：创建/修改/删除/重命名均被捕获；人为丢事件（测试钩子丢弃）后由核对补齐。

### FR-04 双向同步（增/改/删/重命名）

- 本地变更上行，远端变更下行，两者在同一个引擎内串行化。
- 重命名必须保持 `file_id` 不变。

**验收**：[TEST_PLAN.md](TEST_PLAN.md) 中 TC-100 系列全绿。

### FR-05 元数据持久化

- 客户端：SQLite 保存本地索引、待处理队列、游标、冲突记录、应用日志。
- 服务端：SQLite 保存 space、device、entry、version、change_log、operation、blob。

**验收**：kill -9 后重启，队列与索引无丢失、无重复提交（见 [DATABASE.md](DATABASE.md) §8）。

### FR-06 版本管理与幂等提交

- 每次提交携带 `base_revision` 与 `op_id`。
- 服务端 CAS：`base_revision != entry.current_revision` → `409 REVISION_CONFLICT`。
- 相同 `op_id` 重放返回首次结果。

**验收**：并发 10 次相同 `op_id` 提交，`versions` 只增加 0 或 1 行；基于旧版本提交必被拒绝。

### FR-07 变更日志、游标与在线通知

- 每个成功提交在同一事务内追加 `change_log` 行并获得全局 `seq`。
- 客户端按 `seq > cursor` 拉取变更，成功后推进游标并 ACK。
- WebSocket 推送“有新变更”提示，客户端仍需按游标拉取。

**验收**：断开 WS 30 分钟后，仅靠轮询仍能补齐；游标单调不减。

### FR-08 冲突检测、冲突副本与删除标记

- 检测 `modify/modify`、`modify/delete`、`rename/rename`、路径大小写冲突。
- 删除产生 tombstone，不物理删除索引。
- 冲突副本命名与策略见 [CONFLICTS.md](CONFLICTS.md)。

**验收**：S3/S4/S10 场景中两边内容均可找回；冲突在 GUI 中可见。

### FR-09 分块传输、校验、续传与重试

- 大于阈值（默认 8 MiB）的文件分块上传，块大小默认 4 MiB。
- 每块带 SHA-256，整体完成后服务端校验整体 SHA-256。
- 下载支持 HTTP Range 续传。
- 失败重试采用指数退避 + 抖动。

**验收**：上传 100 MiB 文件中断 3 次后续传成功；损坏块被拒绝且不产生版本。

### FR-10 持久化任务队列、断网与崩溃恢复

- 所有待提交操作先落盘再执行。
- 断网时进入 `retry` 状态，不丢操作。
- 启动时扫描未完成操作与应用日志，完成或回滚。

**验收**：断网 30 分钟 + kill -9 + 重启，无操作丢失、无重复版本。

### FR-11 临时文件、安全替换与异常处理

- 所有写入先写 `.syncbox/tmp/` 下的临时文件，`fsync` 后原子替换。
- 磁盘满、权限不足、路径过长、文件被占用均产生明确错误并进入可重试或冲突状态。

**验收**：注入磁盘满后目标文件不被截断；恢复空间后可继续。

### FR-12 跨平台文件系统适配

- 三个平台的监控、原子替换、大小写与 Unicode 规范化差异由独立适配层处理。
- 核心同步逻辑不直接调用平台 API。

**验收**：`libsyncbox_core` 不包含 `#ifdef _WIN32` 之外的平台分支；三平台集成测试通过。

### FR-13 Qt 桌面界面（M7）

- 设备状态、同步进度、失败任务列表、冲突列表与处理入口。
- GUI 通过接口与引擎解耦，不做文件系统操作。

**验收**：GUI 关闭时同步继续；引擎崩溃时 GUI 可提示并重启引擎。

### FR-14 身份认证、TLS、路径安全、权限与设备撤销

- 所有非本地回环通信强制 TLS。
- 路径必须为相对路径，拒绝 `..`、绝对路径、盘符、NUL、控制字符。
- 设备撤销立即生效。

**验收**：[SECURITY.md](SECURITY.md) §7 的路径穿越测试集全部拒绝。

### FR-15 测试体系

- 单元测试（Google Test）、集成测试（真实服务端 + 客户端 + 临时目录）、故障注入、跨平台、性能基准。

**验收**：CI 三平台全绿；核心模块行覆盖率 ≥ 70%，冲突/恢复模块 ≥ 85%。

### FR-16 工程交付物

- CMake 构建脚本、CI、安装与运行文档、架构图、演示脚本、求职项目说明。

**验收**：全新机器按 README 可在 20 分钟内构建并跑通演示。

## 6. 非功能需求

### 6.1 性能

| 编号 | 指标 | 目标 |
|---|---|---|
| NFR-P1 | 增量单文件同步延迟（LAN，WS 在线） | p95 ≤ 2 s |
| NFR-P2 | 100 MiB 文件同步耗时（LAN 1 Gbps） | ≤ 60 s |
| NFR-P3 | 10,000 文件 / 5 GiB 首次同步 | ≤ 10 min |
| NFR-P4 | 空闲 CPU（单核占比） | ≤ 1% |
| NFR-P5 | 10,000 文件时客户端常驻内存 | ≤ 200 MiB |
| NFR-P6 | 服务端吞吐（4 核 / 8 GiB / SSD） | ≥ 100 ops/s，50 设备并发 |
| NFR-P7 | 事件突发（1 秒 1,000 次写入同一文件） | 合并为 ≤ 3 次提交 |

### 6.2 可靠性

| 编号 | 指标 |
|---|---|
| NFR-R1 | 任意阶段崩溃后可自动恢复，无需人工介入 |
| NFR-R2 | 幂等：重复请求不产生重复版本 |
| NFR-R3 | 最终一致：所有设备在线后内容哈希与服务器一致 |
| NFR-R4 | 数据丢失为 0（冲突副本兜底） |

### 6.3 安全

见 [SECURITY.md](SECURITY.md)。摘要：TLS 1.2+、不透明 Bearer token、路径穿越防护、设备撤销、服务端不信任客户端哈希（自行校验）、日志脱敏。

### 6.4 可移植性

- Linux（glibc ≥ 2.28）、Windows 10 1809+、macOS 12+。
- 编译器：GCC 9+ / Clang 12+ / MSVC 19.29+。
- 文件路径统一以 UTF-8 + `/` 表示，内部使用 `std::filesystem::path` 转换。

### 6.5 可维护性

- 模块边界见 [ARCHITECTURE.md](ARCHITECTURE.md)，依赖方向单向。
- 所有公共接口有契约测试。
- 文档与实现不一致时以“显式差距记录”处理，不得静默修改语义。

## 7. 范围边界（v1 明确不做）

| 不做项 | 原因 |
|---|---|
| 移动端客户端 | 超出三平台目标 |
| 端到端加密 | v1 先做 TLS，E2EE 需密钥管理设计，列入 v2 |
| 选择性同步 / 占位文件 | 增加状态复杂度，v1 全量镜像 |
| 多 space 单进程 | v1 一个客户端进程一个 space（协议已预留字段） |
| 文件锁 / 强制单写者 | 与离线优先冲突，改用冲突副本 |
| 历史版本浏览与一键回滚 | 服务端保留 versions 表，UI 回滚列入 v2 |
| 实时协作编辑 | 不在文件同步范畴 |
| 服务端高可用集群 | v1 单节点 SQLite |
| 符号链接、设备文件、FIFO | 默认忽略并记录警告 |
| 文件权限/ACL/扩展属性同步 | v2 候选 |

## 8. 架构不变量（跨文档强约束）

以下规则在需求层面冻结，任何实现不得违反；各设计文档必须与之保持一致。

| 编号 | 不变量 |
|---|---|
| INV-1 | `revision` 只能由服务端在成功事务内 +1，客户端不得自增 |
| INV-2 | `content_hash` 由服务端重新计算校验，不信任客户端声明 |
| INV-3 | `change_log` 追加与 `entries`/`versions` 更新在**同一 SQLite 事务**内完成 |
| INV-4 | 任何会覆盖本地未提交修改的远端变更，必须先解决本地待处理操作 |
| INV-5 | 删除只产生 tombstone，不物理删除 `entries` 行 |
| INV-6 | 冲突时内容不得丢失：要么保留在原路径，要么写入冲突副本 |
| INV-7 | 客户端游标只增不减；游标失效时走全量快照而不是猜测 |
| INV-8 | 客户端自身写入产生的文件系统事件必须被抑制，不得形成反馈循环 |
| INV-9 | 同一 `file_id` 同时最多一个在途提交操作 |
| INV-10 | 临时文件永不直接出现在同步目录中；替换必须是原子的 |

## 10. 已知产品风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 大目录首次全量核对慢 | 首同步体验差 | 分页快照 + 并行下载（M9 调优） |
| 冲突副本过多造成困扰 | 可用性下降 | GUI 聚合展示、批量处理；默认策略保守 |
| Windows 大小写不敏感导致路径冲突 | 同步失败 | 服务端统一 `path_key` 约束（CONFLICTS §7） |
| SQLite 单写者瓶颈 | 服务端吞吐上限 | 写事务短小、WAL、批量提交；v2 可换 PostgreSQL |
| 时钟不同步导致重命名检测误判 | 误判为删除+新建 | 优先使用 `file_id`，时间窗仅作兜底 |
